# Project entry system audit

Scope: the nine public Markdown case studies and their shared project-detail presentation. Source: the repository's case studies, metadata, résumé content, and the supplied HPS work history. No external outcomes or deployment verification were inferred.

## Shared rules

- Use sentence case for editorial headings; preserve names and acronyms. The shared renderer owns heading size, spacing, dividers, body typography, tables, and theme contrast.
- Open with what the project is and the contribution. Put evidence status near the claim it qualifies. Do not present a planned system as an implemented system.
- Technical notes are optional explanations of a specific constraint, decision, mechanism, and evidence boundary. Do not create an empty tab or repeat an existing overview. A dedicated deep dive connects several notes into a traceable system story.
- Keep project-specific distinctions in content and metadata; use the shared renderer and navigation for layout. HPS retains the sole flagship distinction.
- The historical readiness audit records a Kyle-confirmed 100+ work-orders/day workload while the shared résumé reports 120+ requests/week. Their queue and period relationship is not established here; a later résumé reconciliation should resolve presentation across surfaces before merging the figures.
